## Decisions locked so far

- **D1** rules-first enforcement; no server compute in v1; any future trusted ops go to the existing Cloudflare Worker with a quota case + Owner approval.
- **D2** no push notifications for location events in v1 (recipient learns on next open).
- **D3** place alerts v1 = **self-alerts on the owner's own device** (master plan's examples are first-person); recipient-facing alerts = documented future extension.
- **D4** movement classification is device-local, render-time, always labeled an estimate; raw OS-provided speed/bearing are the only stored motion facts.
- **D5** history path = `users/{ownerUid}/locationHistory/{recordId}` (rules-ergonomic owner scoping); `liveLocations` stays exactly as-is with a dual read path for zero-downtime migration.
- **D6** retention cleanup = on-device opportunistic batch deletes on user action (§75-compliant, no sweeps); query-time expiry makes expired records invisible regardless.
- **D7 (Phase 4, 2026-10-31):** the four open questions resolved by their documented defaults, each veto-able at review: (1) v1 scope = Live + Route History + Movement Insights, Place Alerts self-serve last; (2) history granularity = 50 m between retained points; (3) v1 stays **without** `ACCESS_BACKGROUND_LOCATION`; (4) temporary-scope presets = 1 h / 8 h / until-midnight.
- **D8 (Phase 5→8, 2026-11-01):** the Owner's "শুরু করো deeply" instruction is recorded as the Phase 5 verbal go-ahead to begin the implementation waves (6→7→8 landed as one coherent v0.39.0 wave because the engine's history-enqueue and the rules are only meaningful together). Device-review feedback on the Phase 4 screens stays actionable — later waves treat it as normal review input, never as a veto of shipped honesty rules.
- **D10 (Phase 9, 2026-11-01):** four engineering locks discovered while wiring the read path: (a) day queries carry deviceId equality + the retentionExpiresAt floor + the recordedAt day range (the rules' exact contract — "rules are not filters" makes the retention filter MANDATORY in every list, and the resource-dependent authorization get() binds only when deviceId is query-constrained); served by the ONE-TIME composite index (deviceId, retentionExpiresAt, recordedAt) which the SA cannot create (IAM denial) — Owner console action, honest `hist_index_hint` wording until READY; (b) design §6.2's server-side cleanup query (`retentionExpiresAt <= now`) is UNEXECUTABLE under the published rules (the retention floor denies listing expired records) — Phase 9 ships the LOCAL write-log blind-delete variant instead (the engine logs every written docId; deletes need no read; a rules amendment for server-side enumeration is a future item with its own probe cases, never silent); (c) the recipient's day chips show the grant's retention-window days with honest per-day empties (the spec's "days-with-records metadata doc" has no home in the published rules); (d) section B renders the action + retention line without summary chips (quota-protective: chips live on the journey screen where the bounded query already runs — veto-able at review).
- **D9 (Phase 8, 2026-11-01):** two rules-ergonomics locks discovered while writing the enforcement layer: (a) the design's `enabledFeatures` map ships FLATTENED as `liveEnabled`/`historyEnabled` — Firestore rules can `hasOnly()` document keys but not nested map keys, and Phase 8's whole point is server-verifiable field fencing (collection is new in v0.39.0 — no migration); (b) the authz doc carries `recipientKind` ('family'|'guest') so the rules can keep requiring a live pairing for guests after their window lapses (family: the authorization IS the consent — design §4.4 verbatim).

- Revocation-on-stop is best-effort client-side (rules-first): an offline stop queues the revoke and retries on the next user action (Tracking resume / next confirm); the server-side `expiresAt` and the already-deleted live doc bound what a missed revoke can expose. True server-verified revocation-on-stop would need the Worker (D1 deferred class).
- History points are not retried when their write fails offline (design §9 — the next accepted fix supersedes; routes show honest gaps).
- The pending grant/revoke queue lives in SharedPreferences and flushes ONLY on user actions (§75) — no timers, no listeners, no background sweeps.
- Movement classification (Phase 10) and Places rules/geofencing (Phase 11) are untouched future phases; P/E probe series land with them.

## Known honest edges (Phase 9 wave)

- **Composite index prerequisite (Owner console action):** the day queries need the one-time composite index on `locationHistory` (deviceId ASC, retentionExpiresAt ASC, recordedAt ASC, collection-group scope). The coordinator SA can LIST indexes but is DENIED create (`datastore.indexes.create` IAM missing). Until READY, history screens show the honest `hist_index_hint` wording — never routes, never an error storm. The delete-all flow and the owner-side cleanup do NOT need the index (single-field retention-range enumeration on the owner path).
- **Day chips = retention-window days** (D10c): empty days render `hist_none` honestly; exact "days with records" needs a metadata doc the published rules cannot carry (future rules-amendment track).
- **"Delete today" enumerates from the LOCAL write log** (D10b): records written by other devices or pre-log versions are covered only by "delete everything" (server-side enumeration); v0.39.0 was never installed by the Owner, so no pre-log records exist in practice.
- **Multi-inequality runtime risk, honestly disclosed:** the day query (equality + two ranges + matching orderBy) is the documented Firestore construction for BOM 33.4.0, but it could not be executed from the sandbox (no device) — the first real-device run is the Owner's; a wrong shape would surface as FAILED_PRECONDITION with Firestore's own index-link message, rendered by the honest hint path.
- **PERMISSION_DENIED on a day renders "not kept"** (`hist_none`): an expired-in-range edge (retention policy narrowed mid-window) reads as "no records for this day" — the honest wording for records that are no longer kept.
- **ONCE semantics (carried from Phase 8, awaiting Owner ruling):** "sends a single position, then sharing stops by itself" deletes the live doc immediately; if the Owner prefers "last-known stays visible until it goes stale", it is a one-line change at review.
