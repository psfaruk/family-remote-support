## Decisions locked so far

- **D1** rules-first enforcement; no server compute in v1; any future trusted ops go to the existing Cloudflare Worker with a quota case + Owner approval.
- **D2** no push notifications for location events in v1 (recipient learns on next open).
- **D3** place alerts v1 = **self-alerts on the owner's own device** (master plan's examples are first-person); recipient-facing alerts = documented future extension.
- **D4** movement classification is device-local, render-time, always labeled an estimate; raw OS-provided speed/bearing are the only stored motion facts.
- **D5** history path = `users/{ownerUid}/locationHistory/{recordId}` (rules-ergonomic owner scoping); `liveLocations` stays exactly as-is with a dual read path for zero-downtime migration.
- **D6** retention cleanup = on-device opportunistic batch deletes on user action (§75-compliant, no sweeps); query-time expiry makes expired records invisible regardless.
- **D7 (Phase 4, 2026-10-31):** the four open questions resolved by their documented defaults, each veto-able at review: (1) v1 scope = Live + Route History + Movement Insights, Place Alerts self-serve last; (2) history granularity = 50 m between retained points; (3) v1 stays **without** `ACCESS_BACKGROUND_LOCATION`; (4) temporary-scope presets = 1 h / 8 h / until-midnight.
- **D8 (Phase 5→8, 2026-11-01):** the Owner's "শুরু করো deeply" instruction is recorded as the Phase 5 verbal go-ahead to begin the implementation waves (6→7→8 landed as one coherent v0.39.0 wave because the engine's history-enqueue and the rules are only meaningful together). Device-review feedback on the Phase 4 screens stays actionable — later waves treat it as normal review input, never as a veto of shipped honesty rules.
- **D11 (Phase 10, 2026-11-01):** the movement-insights engineering locks: (a) kind boundaries in km/h — STILL < 2, WALK 2–7, CYCLE 7–25 (running lands here too: no RUN kind exists, "possibly" is the honest word), VEHICLE > 25; plausibility ceiling 120 km/h and floor 0 (impossible speeds are REJECTED into the honest "unavailable" line, never clamped); point-delta evidence carries a 15 m jitter floor (the 50 m write throttle filters rests at the source; this is the read-side second line) and only non-gap pairs (≤ 10 min, strictly-greater rule, same threshold the route renderer dashes out) with dt > 0; (b) confidence words = evidence class — MODERATE only when the record carries the OS-provided speed (sensor-backed fact), LIMITED for points-based deltas; (c) staleness — classifyLive rejects observations older than 300 s (the Offline freshness horizon) so a dead session's speed never presents as current, while journey-tail estimates never staleness-reject (historical by nature; the card's observedAt line discloses); (d) journey-tail evidence ladder — last record's plausible OS speed → the most recent non-gap pair (walked back from the tail so an end-of-journey gap doesn't hide the last real stretch) → the honest "unavailable"; a glitched sensor speed falls through to the pair; (e) **the detail screen's section C ships HIDDEN** — liveLocations' published hasOnly carries NO motion facts (the engine writes speed only to history records), a per-open day query just for the card would read up to 1000 records a visit (half the daily free read quota — rejected on §75 grounds), so the card's v1 home is the journey screen where records are already in hand; the activation path is a POST-GATE rules wave (optional speedMetersPerSecond on liveLocations + engine passes fix.speed + a probe case) — classifyLive and its tests already ship, so that wave touches rules + engine only; (f) the enums moved to the classifier (it owns its vocabulary); LiveLocationView/HistoryPoint gained optional speed fields (default null — forward wiring).
- **D10 (Phase 9, 2026-11-01):** four engineering locks discovered while wiring the read path: (a) day queries carry deviceId equality + the retentionExpiresAt floor + the recordedAt day range (the rules' exact contract — "rules are not filters" makes the retention filter MANDATORY in every list, and the resource-dependent authorization get() binds only when deviceId is query-constrained); served by the ONE-TIME composite index (deviceId, retentionExpiresAt, recordedAt) which the SA cannot create (IAM denial) — Owner console action, honest `hist_index_hint` wording until READY — **CORRECTED 2026-11-01 (Phase 10): live Admin-REST test of the exact query shape proves Firestore serves it with ZERO composite indexes (single-field merge); the console action was removed and the index demoted to an optional perf tool (scripts/create-location-index.mjs)**; (b) design §6.2's server-side cleanup query (`retentionExpiresAt <= now`) is UNEXECUTABLE under the published rules (the retention floor denies listing expired records) — Phase 9 ships the LOCAL write-log blind-delete variant instead (the engine logs every written docId; deletes need no read; a rules amendment for server-side enumeration is a future item with its own probe cases, never silent); (c) the recipient's day chips show the grant's retention-window days with honest per-day empties (the spec's "days-with-records metadata doc" has no home in the published rules); (d) section B renders the action + retention line without summary chips (quota-protective: chips live on the journey screen where the bounded query already runs — veto-able at review).
- **D9 (Phase 8, 2026-11-01):** two rules-ergonomics locks discovered while writing the enforcement layer: (a) the design's `enabledFeatures` map ships FLATTENED as `liveEnabled`/`historyEnabled` — Firestore rules can `hasOnly()` document keys but not nested map keys, and Phase 8's whole point is server-verifiable field fencing (collection is new in v0.39.0 — no migration); (b) the authz doc carries `recipientKind` ('family'|'guest') so the rules can keep requiring a live pairing for guests after their window lapses (family: the authorization IS the consent — design §4.4 verbatim).
