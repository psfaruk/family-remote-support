## Decisions locked so far

- **D1** rules-first enforcement; no server compute in v1; any future trusted ops go to the existing Cloudflare Worker with a quota case + Owner approval.
- **D2** no push notifications for location events in v1 (recipient learns on next open).
- **D3** place alerts v1 = **self-alerts on the owner's own device** (master plan's examples are first-person); recipient-facing alerts = documented future extension.
- **D4** movement classification is device-local, render-time, always labeled an estimate; raw OS-provided speed/bearing are the only stored motion facts.
- **D5** history path = `users/{ownerUid}/locationHistory/{recordId}` (rules-ergonomic owner scoping); `liveLocations` stays exactly as-is with a dual read path for zero-downtime migration.
- **D6** retention cleanup = on-device opportunistic batch deletes on user action (§75-compliant, no sweeps); query-time expiry makes expired records invisible regardless.
- **D7 (Phase 4, 2026-10-31):** the four open questions resolved by their documented defaults, each veto-able at review: (1) v1 scope = Live + Route History + Movement Insights, Place Alerts self-serve last; (2) history granularity = 50 m between retained points; (3) v1 stays **without** `ACCESS_BACKGROUND_LOCATION`; (4) temporary-scope presets = 1 h / 8 h / until-midnight.
- **D8 (Phase 5→8, 2026-11-01):** the Owner's "শুরু করো deeply" instruction is recorded as the Phase 5 verbal go-ahead to begin the implementation waves (6→7→8 landed as one coherent v0.39.0 wave because the engine's history-enqueue and the rules are only meaningful together). Device-review feedback on the Phase 4 screens stays actionable — later waves treat it as normal review input, never as a veto of shipped honesty rules.
- **D9 (Phase 8, 2026-11-01):** two rules-ergonomics locks discovered while writing the enforcement layer: (a) the design's `enabledFeatures` map ships FLATTENED as `liveEnabled`/`historyEnabled` — Firestore rules can `hasOnly()` document keys but not nested map keys, and Phase 8's whole point is server-verifiable field fencing (collection is new in v0.39.0 — no migration); (b) the authz doc carries `recipientKind` ('family'|'guest') so the rules can keep requiring a live pairing for guests after their window lapses (family: the authorization IS the consent — design §4.4 verbatim).

## Known honest edges (Phase 8 wave)

- **ONCE scope semantics (recorded for review):** "sends a single position, then sharing stops by itself" — the one accepted fix is written, then the FULL existing stop path runs (spec's words), so the live doc is deleted immediately: a recipient with the Tracking tab open sees the position arrive in real time, afterwards honest absence. If the Owner prefers "last-known stays visible until it goes stale", that is a one-line change at Phase 9 review — flagged, not silently decided.
- The History **screen** (real relId) still shows the honest empty state — the query + summary wiring is Phase 9's deliverable; the data path (engine writes + rules reads + probes) is live as of this wave.
- Detail screen section E (recipient side) still renders the Phase 4 honest placeholders ("retention: none / history access: none") — real values arrive with Phase 9 when the recipient reads their own authz doc.
- Revocation-on-stop is best-effort client-side (rules-first): an offline stop queues the revoke and retries on the next user action (Tracking resume / next confirm); the server-side `expiresAt` and the already-deleted live doc bound what a missed revoke can expose. True server-verified revocation-on-stop would need the Worker (D1 deferred class).
- History points are not retried when their write fails offline (design §9 — the next accepted fix supersedes; routes show honest gaps).
- The pending grant/revoke queue lives in SharedPreferences and flushes ONLY on user actions (§75) — no timers, no listeners, no background sweeps.
- Movement classification (Phase 10) and Places rules/geofencing (Phase 11) are untouched future phases; P/E probe series land with them.
